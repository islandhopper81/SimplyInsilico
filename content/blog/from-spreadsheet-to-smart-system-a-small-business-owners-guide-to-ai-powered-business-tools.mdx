## The Problem We Are Solving

Every business that grows intentionally is running some version of the same experiment: if we do X enough times, will we see Y?

A sales team makes calls and tracks demos booked. A marketing team runs campaigns and tracks leads generated. A service business follows up with past clients and tracks referrals received. The activity is different. The question is the same: are our efforts producing results?

Most small businesses track this in a spreadsheet. Some track it in their heads. Very few have a system that makes the connection between effort and outcome visible, automatic, and accessible to everyone on the team.

We built one and called it the Effort to Outcome Tracker. It is a simple tool that lets a small team log their activities, record their results, and see how the two connect over time. Nothing about the idea is complicated. But the decisions about how to build it — where data lives, who can access it, what it costs to run, and how secure it is — turn out to be exactly the decisions every small business owner faces when they consider adding AI to their operations.

So we built it six times. Each time we made different choices. Each time we learned something different. And each time the result was a working tool with a distinct set of tradeoffs that make it right for some businesses and wrong for others.

That is what this series is about.

## Why Architecture Matters — Even If You Never Write a Line of Code

When most people hear the word "architecture" in a technology context they assume it is a conversation for developers. It is not. It is a conversation for business owners.

The architectural decisions behind a software tool determine things you care about deeply:

**Where your data lives.** Is it on your computer, in a third-party cloud, or somewhere in between? Who can access it? What happens if you stop paying for the service? For businesses handling sensitive client information — legal practices, medical offices, financial advisors — this is not a technical question. It is a liability question.

**What it costs to run.** Some tools cost nothing after setup. Others charge per user, per month, per query, or per record. Understanding the cost model before you build means no surprises six months in when the bill arrives.

**How much technical help you need.** Some architectures require a developer to set up and maintain. Others can be managed by anyone on your team with a basic comfort level for technology. Knowing which is which determines whether you are creating a dependency or building something you own.

**How it scales.** A tool that works beautifully for three people may become unreliable or expensive for fifteen. The right architecture for where your business is today may not be the right architecture for where it is going.

These are business decisions. They happen to have technical answers. Our job is to translate between the two.

## What We Built — And How We Built It Six Ways

The Effort to Outcome Tracker is a web-based tool with three core features: a form to log an activity, a form to record a result, and a dashboard that shows how the two connect over time. Simple by design. The simplicity is the point — it keeps the focus on the architectural decisions rather than the features.

Here is a preview of what each module covers and who it is most relevant for:

**Module 1: The No-Infrastructure Option**
We built the tracker using only Claude's built-in storage system. No database. No server. No accounts to manage. It took about five minutes and worked immediately. It also stopped working the moment a second person tried to use it. This module teaches you what "zero infrastructure" actually means — and what you give up to get it.
Right for: solo users, quick prototypes, internal calculators and reference tools.

**Module 2: The Cloud Database Option**
We added a real shared database using Supabase — a managed cloud platform that handles data storage, security, and access without requiring a server. Team members could log activities from any device and see each other's entries in real time. This is the architecture that most small business web tools are built on.
Right for: small teams, shared data, tools that need to be accessible from anywhere.

**Module 3: The Keep-It-Local Option**
We moved everything off the cloud and onto a single machine, then used a Cloudflare Tunnel to make it accessible from anywhere without exposing the machine to security risks. The data never left the building. This module is for businesses where data privacy is not a preference — it is a requirement.
Right for: legal practices, medical offices, financial advisors, any business with strict data confidentiality requirements.

**Module 4: The No-Code Backend Option**
We replaced traditional server code with n8n — a visual automation tool that lets non-technical users build and modify the business logic behind an application without writing a single line of code. The backend became something anyone on the team could understand and change.
Right for: teams without dedicated technical staff, integration-heavy workflows, businesses that need to own and modify their own tools.

**Module 5: The Full Cloud Stack with AI**
We deployed a professionally hosted frontend, kept the Supabase database from Module 2, and added Claude as an intelligence layer on top — connected directly to the database via a secure MCP connector. The result was a tool where you could ask questions in plain English and get answers, charts, and analysis back in seconds. No pre-built dashboard required.
Right for: businesses that want analytical capability without hiring a data analyst, teams doing periodic reporting and strategic review.

**Module 6: The Production-Ready Option**
We took the full cloud architecture from Module 5 and rebuilt it with the engineering practices that separate a prototype from a system you can rely on: automated deployment, server-side security, environment management, and a proper development workflow. This is what it looks like when you build something meant to last.
Right for: businesses that are serious about a long-term AI-powered tool, teams that expect the system to grow and evolve over time.

By the time you have read all six posts you will be able to answer the following questions about any AI-powered tool you are considering for your business:
